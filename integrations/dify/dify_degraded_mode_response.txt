Recorded example: correct behaviour when the MCP server was unreachable
=========================================================================

This replaces the earlier version of this file (a single mid-conversation 503, seen
under the app's older 6-rule prompt). The scenario below is a cleaner, complete test
of the same behaviour, reported by the person running the Dify app: before restarting
the MCP server on the host, EVERY tool call returned a 503 from the MCP proxy. The app
(now running the current 8-rule prompt in integrations/dify/system_prompt.md) did not
answer from its own knowledge for any of them. For each call it correctly reported that
the corresponding piece of information was pending, quoted the connection error, and
gave no time or cost figure for the failed call (rule 5: "If a tool fails or returns
nothing, say so, quoting its error message. Do not fill the gap from your own
knowledge, and do not invent a time or cost for a failed call.").

The error shape matches the "红线"/rule-1 example already recorded in the Dify
build-mode config note baked into the app (integrations/dify/interface-adjudicator-qa.yml):

    tool invoke error: Failed to connect to MCP server: code=503 message="Server
    error '503 Service Unavailable' for url 'http://host.docker.internal:8765/mcp'"

After the MCP server was restarted, the same questions were re-run successfully; see
integrations/dify/dify_q1.png and dify_q2.png, and docs/dify_setup.md section A6 for
what was checked in that run (including two citations that were verified against live
tool output).

Provenance: this text is the human's own transcription of what they saw in the Dify UI
at the time; no screenshot or raw log of the all-503 exchange was saved.
